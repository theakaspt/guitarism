# 기타 이론 앱 — 개발 보고서 3부 (v45 → Vite 이관 · 안정성 · UI/UX)

**목적:** 1·2부(단일 `.jsx` 파일 + 수동 번들 시절)에 이어, 세 번째 작업 세션에서 진행한 **프로젝트 재구성(Phase 0)** · **안정성 보강(Phase 1)** · **UI/UX(Phase 2)** 의 결정 지점·이슈·검증 방법을 검토·수정 담당자에게 전달.
**대상:** `guitar-theory-app.jsx` 단일 파일 → Vite + React 프로젝트
**이 세션의 범위:** 작업지시서 **Phase 0 · 1 · 2**. **Phase 3(디자인 패스 2차)는 손대지 않음** — 발주자가 명시적으로 시작을 요청할 때만 진행하도록 지시서에 못박혀 있다.
**Phase 0 완료 조건:** "화면과 소리가 지금 배포본(v45)과 동일함" — 달성(§5-K)
**Phase 1 완료 시점까지** 아홉 화면 HTML이 v45와 완전히 같았다(새로 넣은 것들은 문제가 났을 때만 나타나므로). Phase 2부터는 화면을 의도적으로 바꿨다.

## 1. 이 세션의 범위

먼저 Phase 0(이관)만 끝내고 실기기(아이폰) 확인을 받은 뒤 Phase 1(안정성)로, 이어서 Phase 2(UI/UX)로 넘어갔다. "이관이 끝나기 전에는 기능·디자인 변경을 섞지 않는다"는 원칙을 지키기 위해 Phase 0과 그 뒤를 확실히 끊었다. Phase 3(디자인 패스 2차)은 지시서 §7의 조건(발주자의 명시적 요청 + 변경 전후 스크린샷 승인) 때문에 시작하지 않았다.

| 영역 | v45 → 이번 |
|---|---|
| 소스 | 단일 `guitar-theory-app.jsx` 1,827줄 | `src/` 아래 22개 모듈 |

## 2. 진행 순서

1. 저장소 클론 → 보고서 1·2부 정독 → 소스 1,827줄 구조 파악
2. 최상위 선언 블록 파서를 만들어 **모든 줄이 정확히 한 블록에만 속하도록** 분해 (누락·중복 0줄 확인)
3. 블록을 목표 모듈에 배치. **본문은 한 글자도 고치지 않고**, 선언 줄 앞에 `export`만 붙임
4. 예외적으로 `Scales` 컴포넌트 안의 순수 계산 3개만 파일 밖으로 이동(§3-3) → **6,708건 전수 대조로 결과 동일 확인**
5. Vite 프로젝트 구성 + `vite-plugin-pwa`
6. Vitest 테스트 8종 작성
7. **v45 배포 번들과 새 빌드의 화면 HTML 대조**(9개 화면, 완전 일치)
8. README·보고서 작성 → **발주자 아이폰 확인 완료 · GitHub push · Vercel 배포 완료**
9. (Phase 1) 설정 영속 → 에러 화면 → 스케줄러 견고화 → 화면 꺼짐 방지 → iOS 소리 안내 순으로 제작
10. 검사 4종 추가(31개) 후 **v45 화면 대조 재실행 → 여전히 아홉 화면 완전 일치**
11. (Phase 2) 보이싱 보기 → 접근성 → 코치마크 → 고프렛 보정 → 잔손질 순으로 제작
12. **실제 브라우저(아이폰 크기)로 스크린샷을 찍어** 잘림·넘침을 눈으로 확인, 검사 4종 추가(26개)

## 3. 주요 고민 지점 & 결정

### 3-1. 새 버전 알림: 자동 새로고침 vs 물어보기

작업지시서는 `vite-plugin-pwa`의 **autoUpdate + 토스트**를 권했다. 그런데 autoUpdate는 새 버전을 감지하면 **화면을 알아서 새로고침한다.** 이 앱은 잼 반주가 계속 도는 앱이라, 연습 도중에 화면이 새로고침되면 소리가 끊긴다.

→ `registerType: "prompt"` + **"새 버전이 준비됐어요 → [새로고침] [나중에]"** 알림으로 결정. 지시서가 원한 결과("캐시명 수동 변경 절차를 완전히 대체")는 그대로 달성하면서, 새로고침 시점만 사용자가 고르게 했다. 알림은 새 버전이 실제로 올라왔을 때만 나타나므로 평소 화면은 v45와 동일하다.

### 3-2. React StrictMode를 켜지 않음

Vite의 React 템플릿은 기본으로 `StrictMode`를 켠다. StrictMode는 개발 모드에서 이펙트를 **일부러 두 번 실행**해 문제를 드러내는 장치인데, 이 앱은 잼 스케줄러가 이펙트 안에 있어(절대 규칙 5) 개발 중에 반주가 잠깐 두 겹으로 예약될 수 있다. "지금 배포본과 동일하게"라는 이관 원칙에 어긋나므로 켜지 않았다.

→ Phase 1에서 스케줄러를 견고화할 때 다시 검토할 것. (`src/main.jsx`에 이유를 주석으로 남겨 뒀다.)

### 3-3. `Scales` 안의 계산 3개만 파일 밖으로 뺀 이유

분할 원칙은 **"이동만, 수정 금지"** 였다. 딱 한 군데 예외를 뒀다. `Scales` 컴포넌트 안에 `build3nps`(3음/줄), `diagFrom`(대각선), CAGED 위치 계산이 **클로저로** 들어 있었는데, 이 상태로는 작업지시서 §4-3이 요구한 `theory-scales.test`(3nps 756개, CAGED 서명, 대각선 프렛 유효성)를 **실제 코드에 대고** 검사할 수 없다. 테스트가 같은 계산을 베껴 쓰면 "테스트와 앱이 따로 노는" 상태가 된다.

→ 본문은 그대로 두고 **클로저로 읽던 변수(`root`, `ivset`, `N`)만 인자로 바꿔** `theory/scales.js`로 옮겼다. 그리고 원본 클로저를 그대로 복사한 참조 구현과 **전 스케일 13종 × 12루트 × 전 시작위치 = 6,708건**을 대조해 결과가 완전히 같음을 확인했다.

### 3-4. ErrorBoundary는 Phase 1로 미룸

작업지시서 §4-1의 목표 구조에는 `main.jsx`에 ErrorBoundary가 적혀 있지만, 같은 문서 §5-2에서 폴백 화면 문구("문제가 생겼어요")와 "다시 시작" 버튼까지 Phase 1 항목으로 명세돼 있다. 절반만 지금 만들면 Phase 1에서 다시 뜯어야 하고, 이관 단계에서 화면 요소를 늘리지 않는다는 원칙에도 어긋난다.

→ **Phase 1에서 명세대로 한 번에** 만들기로 하고 이번엔 넣지 않았다. (발주자에게 보고 완료)

### 3-5. 서비스워커 폴백 범위

예전 `sw.js`는 실패한 **모든 GET**에 `index.html`을 돌려줬다(자산 요청에도 HTML이 감 — 지시서 §5-6이 지적한 문제). 새 설정은 `navigateFallback`을 화면 이동 요청에만 적용한다. `tests/dist.test.js`가 빌드된 `sw.js`에 `NavigationRoute`가 들어 있는지 확인한다.

### 3-6. 이관 전 원본을 저장소에 남김

`docs/legacy/`에 이관 직전의 `guitar-theory-app.v45.jsx`와 `bundle.v45.js`를 넣었다. 이유는 두 가지다. ① 전수 대조표(`npm run inventory`)와 v45 화면 대조(`npm run compare:v45`)를 **언제든 다시 돌릴 수 있게** 하기 위해. ② 이관 과정에서 뭔가 달라졌다는 의심이 들 때 원본을 바로 열어 볼 수 있게 하기 위해. Phase 1에서 화면을 바꾸기 시작하면 `compare:v45`는 당연히 달라지므로, 평소 `npm test`에서는 건너뛰도록 해 뒀다.

### 3-7. (Phase 1) 예약 창을 상황에 따라 바꾼 이유

작업지시서 §5-3은 "선행예약 창을 늘리거나(예: 0.5~1s) `visibilitychange` 대응"을 제안했다. 그런데 예약 창을 늘리면 **재생 중에 키·리듬·음색을 바꿨을 때 이전 소리가 그만큼 더 들린다.** 이미 예약해 둔 소리는 취소할 수 없기 때문이다. 연주자가 잼을 돌리며 키를 바꾸는 것이 이 앱의 핵심 사용 패턴이라, 반응이 1초 느려지는 건 큰 손해다.

→ **화면을 보고 있을 때 0.15초(지금과 같음), 화면이 가려지면 1.5초**로 자동 전환. 가려진 동안에는 어차피 설정을 바꿀 수 없으니 반응 속도를 포기해도 잃는 게 없다. 전환은 `visibilitychange`에서 하고, **가려지는 그 순간 곧바로 한 번 채운다**(가려진 뒤에는 타이머가 늦춰져서 채울 기회를 놓치기 때문). 발주자가 세 선택지 중 이 방식을 골랐다.

### 3-8. (Phase 1) 저장 계층을 화면과 분리한 방식

작업지시서 §5-1의 핵심 요구는 "직접 localStorage 호출을 컴포넌트에 흩뿌리지 말 것 — 추후 Supabase 전환 시 이 파일만 교체"였다. `src/storage.js` 하나에 `get`/`set`/`clearAll`을 두고, 화면에서는 `useStored(이름, 기본값, 검사기)` 하나만 쓴다. 컴포넌트 코드에 `localStorage`라는 단어가 한 번도 나오지 않는다.

**검사기(`intIn`·`oneOf`)를 붙인 이유:** 저장한 뒤 목록이 줄어들 수 있다. 스케일이 13종일 때 12번을 저장했는데 나중에 10종이 되면, 복원하는 순간 `SCALES[12]`가 `undefined`가 되어 화면이 죽는다. 검사기가 범위를 벗어난 값을 버리고 기본값으로 돌린다.

**저장하지 않는 것:** 재생 여부(앱을 켜자마자 소리가 나면 안 된다), 포지션 번호(스케일·코드를 바꾸면 어차피 0으로 돌아간다).

### 3-9. (Phase 1) 에러 화면에 "설정까지 초기화"를 넣은 이유

설정을 저장하기 시작하면 새로운 실패 방식이 생긴다. **저장된 값이 꼬여서 켤 때마다 같은 자리에서 죽는 상황**이다. 이러면 "다시 시작"을 눌러도 같은 값을 다시 읽어 또 죽는다(무한 루프). 그래서 폴백 화면에 저장된 설정을 지우고 시작하는 버튼을 하나 더 뒀다. 작업지시서에 없던 항목이지만, 영속 기능을 넣는 순간 함께 필요해지는 안전장치다.

배치는 **최상위 1개 + 탭 단위 1개**(`key={tab}`)로 했다. 탭 단위 경계에 `key`를 주면 다른 탭에 갔다 오는 것만으로 자동 복구가 시도된다. 잼 바는 따로 감싸서, 화면이 죽어도 반주는 계속 돌게 했다.

### 3-10. (Phase 2) 스케줄러에서 화면으로 상태를 넘기는 방법

지시서 §6-1은 "스케줄러에서 UI로의 상태 전달은 60fps 리렌더를 유발하지 않는 방식(코드 단위 이벤트)으로"라고 못박았다. 잼 스케줄러는 25ms마다 도는데, 여기서 화면 상태를 갱신하면 초당 40번 리렌더가 일어난다.

→ 타임라인 이벤트에 **"몇 번째 코드인지"(`ci`)** 를 달아 두고, 스케줄러가 **코드가 바뀌는 순간에만** `setTimeout`으로 그 시각에 맞춰 화면에 알린다. 4마디 진행이면 한 바퀴에 3~4번 갱신된다. 소리는 미리 예약해 두고 화면은 실제로 울리는 시점에 바뀌므로, 눈과 귀가 어긋나지 않는다.

보이싱을 지판에 그리려면 음높이(midis)만으로는 부족하고 **줄·프렛**이 필요하다. `voiceProgression`을 `voiceProgressionFull`(후보 객체 그대로)과 기존 함수(음만 추출)로 나눴다 — 계산 자체는 손대지 않았고, **1,728가지 조합의 타임라인을 Phase 0 시점 코드와 대조해 소리가 한 음도 달라지지 않았음**을 확인했다(§5-N).

### 3-11. (Phase 2) 가이드톤을 강조한 이유

지시서가 "가이드톤(3·7음) 강조"를 지정한 것은 재즈 컴핑 학습의 핵심이기 때문이다. 코드의 성격(메이저/마이너/도미넌트)은 3음과 7음이 결정하고, 루트와 5음은 베이스가 치므로 기타는 생략해도 된다. 지판에서 이 두 음이 어디 있는지 눈에 익으면 다른 보이싱으로 옮겨 갈 수 있다.

구현은 `FORMULA[타입]`의 2번째·4번째 값(3음·7음)을 금색으로 칠하는 것이다. 잼에 쓰는 네 타입(m7·7·maj7·m7♭5)이 모두 [루트, 3음, 5음, 7음] 4음 구조라 규칙이 단순하게 떨어진다.

### 3-12. (Phase 2) 고프렛 잘림은 "위치 보정"이 아니라 "지판 확장"으로

지시서 §6-4는 "표시 범위를 동적으로 확장하거나 시작 위치를 한 옥타브 보정"이라는 두 방법을 제시했다. 확인해 보니 **3음/줄 포지션에서 16~17프렛을 쓰는 음이 142개** 있었고, 지판을 15프렛까지만 그려서 그 음들이 화면에서 사라지고 있었다.

시작 위치를 옥타브 보정하면 **사용자가 고른 포지션과 다른 자리를 보여 주게 된다**(7개 포지션 중 높은 것들을 못 보게 되는 셈). 그래서 **지판을 필요한 만큼(최대 17프렛까지) 늘려 그리는 쪽**을 택했다. 포지션이 낮으면 예전처럼 15프렛까지만 그린다.

### 3-13. (Phase 2) "어쿠스틱" → "클린"

보고서2 §7의 지적("소리는 예쁘나 어쿠스틱 같진 않다")에 대해 지시서는 후보로 "클린"과 "폴크"를 줬다. **"클린"으로 정했다.** 불만의 핵심이 "이름이 통기타를 약속하는데 소리가 안 그렇다"는 것이므로, 통기타를 전혀 약속하지 않는 이름이 문제를 정확히 해결한다. "폴크"는 여전히 어쿠스틱 계열을 암시한다.

**내부 키(`acoustic`)는 그대로 뒀다.** 저장된 설정과 코드 전체에 영향이 가고, 이름 바꾸기의 목적(화면 표시)과는 무관하기 때문이다. 화면 글자만 바꾸면 되는 일이다.

### 3-14. (Phase 2) 하지 않은 것 — 251 잼 외 진행의 미니플레이어

지시서 §6-5의 마지막 항목은 "251 잼 외 진행에서도 미니플레이어로 듣기 가능 여부 **검토(발주자 확인 후)**"였다. 확인 없이 진행하지 않았다. 검토 결과만 적어 둔다.

기술적으로는 어렵지 않다. 디코더의 `PROGRESSIONS`(5종)를 `JAM_FORMS` 형식(도수 + 코드 타입 + 마디 수)으로 옮기면 지금 스케줄러가 그대로 돌린다. 다만 **성격이 다르다.** 지금 잼 폼 6종은 전부 7th 코드(m7·7·maj7·m7♭5)로 된 재즈 진행이고, 컴핑 보이싱도 4음 드롭2 전용이다. 추천 진행 5종은 트라이어드 기반 팝/락 진행이라 같은 보이싱 엔진에 넣으면 **원래 없던 7음이 붙는다.** 트라이어드 컴핑을 따로 만들거나(작업량 큼), 7th를 붙인 채로 들려주거나(장르가 어긋남) 둘 중 하나를 골라야 한다. 발주자 판단이 필요한 지점이다.

## 6. 알려진 한계 / 리스크 (갱신)

- **Vercel 연결은 발주자가 직접 한다.** 저장소 push 권한이 이 작업 환경에 없어 코드는 로컬 폴더로 전달한다. Phase 0은 이 절차로 배포·아이폰 확인까지 완료했다.
- **화면 대조는 JSDOM 기준이다.** HTML 구조·글자·인라인 스타일이 완전히 같음은 확인했지만, 실제 픽셀 렌더와 **소리**는 실기기 확인이 필요하다. 소리 쪽은 코드가 한 줄도 바뀌지 않았다는 점(전수 대조)이 근거다.
- **GitHub Pages 배포본은 그대로 둔 상태다.** 발주자 결정에 따라 Vercel 확인이 끝난 뒤 정리 방법을 다시 논의한다. 그때까지 두 주소가 공존하며, Pages 쪽은 예전 v45가 계속 뜬다.
- **화면 꺼짐 방지는 지원 기기 한정이다.** iOS 사파리는 16.4부터 Screen Wake Lock을 지원한다. 안 되는 기기에서는 조용히 넘어간다(재생은 정상).
- **아이폰 화면을 잠그면 여전히 소리가 멈춘다.** iOS가 오디오 자체를 정지시키기 때문에 웹앱에서 막을 방법이 없다. 다만 이제는 **돌아왔을 때 밀린 소리가 몰아치지 않고**(이슈 #15) 박자를 맞춰 이어진다.
- **무음 스위치 안내는 "장치가 안 깨어난 경우"에만 뜬다.** 지시서 §5-5 명세대로다. 실제 무음 스위치는 오디오 컨텍스트를 멈추지 않고 볼륨만 죽이는 경우가 많아, 이 안내가 항상 뜨지는 않는다.
- **`_row` 상수는 쓰이지 않는다.** 원본에도 쓰이지 않던 죽은 코드지만, 전수 대조에서 "사라진 선언"으로 잡히지 않도록 `theme.js`에 그대로 옮겨 뒀다. 정리는 Phase 2 이후에.
- **접근성은 "기초"까지다.** 화면 낭독기(VoiceOver)로 실제 사용해 본 검증은 아직 없다. 다이얼은 여전히 손가락 전용이며(키보드로 키를 바꿀 수는 없다), 대신 지금 키를 소리 내 읽어 주는 안내는 넣었다.
- **코치마크 위치는 고정값(vh 단위)이다.** 아주 작은 화면(SE 등)에서는 말풍선이 가리키는 대상과 살짝 어긋날 수 있다. 한 번만 뜨는 화면이라 감수했다.
- **`docs/legacy/` 가 저장소 용량을 약 340KB 차지한다.** 대조 재현을 위한 의도적 보존이다. Phase 1이 끝나 화면이 달라지면 `bundle.v45.js`는 지워도 된다.

## 8. 검토 시 유의점 (1·2부에 추가)

1. **분할된 파일 사이를 옮길 때도 전수 대조표를 돌릴 것** — `npm run inventory`. 이슈 #7의 재발 방지 장치다.
2. **`theory/`와 `audio/`는 React에 의존하지 않는다.** 이 경계를 유지해야 테스트가 화면 없이 계산만 검사할 수 있다.
3. **v45 대조(`npm run compare:v45`)는 이제 "차이를 보여 주는 도구"다.** Phase 1까지는 아홉 화면이 완전히 같았지만 Phase 2부터 일부러 달라졌다. 그래서 같은지를 따지지 않고 어느 화면이 얼마나 달라졌는지만 출력한다(화면이 아예 비면 그때만 실패).
7. **잼 계산(`theory/jam.js`)을 고치면 소리 불변 대조를 다시 할 것.** Phase 2에서 쓴 방식(§5-N)대로 이전 버전과 타임라인 1,728건을 비교하면 "화면만 바꾸려다 소리까지 바뀐" 사고를 잡는다.
8. **글자 크기를 다시 줄이지 말 것.** `tests/a11y.test.jsx`가 11px 미만을 막고 있다. 디자인상 꼭 필요하면 그 검사부터 논의할 것.
5. **설정을 새로 저장할 때는 반드시 검사기를 붙일 것.** `useStored(이름, 기본값, intIn(0, 목록길이-1))` 형태. 안 붙이면 목록이 줄어드는 순간 복원하다 죽는다.
6. **잼 스케줄러의 `skipPast`를 지우지 말 것.** 없으면 폰을 잠갔다 돌아올 때 소리가 폭발한다(이슈 #15).
4. **테스트에 박힌 숫자(414 · 1,872 · 756 · 106)는 "지금 규모"의 스냅샷이다.** 데이터를 의도적으로 늘렸다면 숫자를 갱신하고, 의도치 않게 바뀌었다면 원인을 찾을 것.
