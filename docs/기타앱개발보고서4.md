# 기타 이론 앱 — 개발 보고서 4부 (연습 파트너로 전환)

**목적:** 1~3부(기능 골격 → PWA 배포 → Vite 이관·안정성·UI/UX·디자인)에 이어, **2차 작업지시서(연습 기능·학습 콘텐츠)** 의 결정 지점·이슈·검증 방법을 검토·수정 담당자에게 전달.
**대상:** Vite + React 프로젝트 (`theakaspt/guitarism`, Vercel 자동 배포)
**이 세션의 범위:** **Phase A(연습 도구 3종) · B(코드톤 타겟 뷰) · C(꿀팁 + 용어 사전)**. **Phase D(연습 탭)는 시안 제시 후 발주자 판단으로 보류** → 백로그.
**성격:** 새 엔진을 만들지 않고 기존 것(반주 스케줄러·지판 렌더러·소리 엔진·검증된 이론 데이터)을 **조립**했다.

## 2. 진행 순서

1. 개선 제안서·2차 작업지시서 정독 → 저장소가 원격 최신본과 동일함 확인
2. (Phase A) 카운트인 → 컴핑 끄기 → 템포 트레이너 순으로 제작, 검사 13개 추가
3. **절대 규칙 11 증명** — 카운트인이 반주 데이터에 닿지 않음을 1,728건 + 정적 검사로 확인 (§5-R)
4. (Phase C) 시드 팁 10개를 **앱 데이터로 전수 검산** → **2건이 사실과 달라 수정** (§4 이슈 #17·#18)
5. 팁 시스템 + 용어 사전 제작, 검사 21개 추가
6. 옛 GitHub Pages 주소가 **고장 나 있음을 발견** → 이사 안내 페이지 제작 (§4 이슈 #19)
7. (Phase B) 목업본을 따로 만들어 변경 전후 스크린샷 제시 → **승인** → 본체 적용, 검사 9개 추가
8. (Phase D) 와이어프레임 3화면 제시 → **보류 결정** → 백로그 기록

## 3. 주요 고민 지점 & 결정

### 4-1. (Phase A) 카운트인을 타임라인이 아니라 "시작 시각"으로 구현한 이유

지시서 A-1은 두 방법을 줬다 — ① `jamTimeline` 앞에 카운트 이벤트를 붙이거나, ② `loopStart`를 한 마디 뒤로 밀고 카운트 이벤트를 따로 예약. **②를 택했다.**

①은 반주 데이터 자체에 손을 대는 것이라, 절대 규칙 11("소리 불변 대조")을 증명하기가 어려워진다. ②는 `jamTimeline`이 **카운트인을 인자로 받지도 않는** 상태를 유지하므로, "카운트인이 반주에 영향을 줄 통로 자체가 없다"를 구조로 보일 수 있다. 그리고 "루프 반복 시에는 카운트인 없음"이라는 요구도 자연히 만족된다 — 카운트 소리는 재생을 누른 그 순간 딱 한 번 예약되고 타임라인에는 아예 들어가지 않기 때문이다.

**보이스:** 새 음색을 만들지 않고 기존 드럼의 `rim`(사이드스틱)을 재사용했다. 1박만 세게(0.95), 나머지는 약하게(0.6) — 밴드에서 드러머가 세는 방식이다.

**"이번 시작에만" 처리:** `countInPendingRef`를 재생 버튼에서 세우고 스케줄러 설정 때 소비한다. 재생 중에 키·폼을 바꾸면 스케줄러 효과가 다시 도는데, 이때 카운트인이 또 나오면 연습이 끊긴다. ref로 막았다.

### 4-2. (Phase A) 컴핑 끄기 — 타임라인을 나누지 않고 "예약을 건너뛰기"

지시서 A-2가 권한 방식 그대로다. 타임라인을 분기하면 다마디 리듬·베이스 분리 같은 검증된 로직에 갈래가 생겨 회귀 위험이 커진다. 스케줄러에서 `compingRef.current`가 false면 `strumAt`만 건너뛴다.

**핵심은 코드 표시를 남긴 것이다.** 컴핑이 꺼져도 `nowChord` 갱신은 그대로 돈다. 이 모드의 사용법이 "드럼만 들으며, 화면의 코드를 보고 내가 직접 친다"이기 때문이다. 소리를 끄면서 화면까지 멈추면 모드 자체가 무의미해진다. `tests/sound-unchanged.test.js`가 `setNowChord`가 컴핑 조건 블록 **밖**에 있는지 소스 구조로 확인한다.

**드럼 강제 ON 문제:** 지시서는 "드럼 OFF + 컴핑 OFF 동시엔 무음 재생 방지"를 요구했는데, 확인해 보니 현재 구조에서 드럼은 상시 재생이라 무음이 될 경로가 없다. 그래서 추가 방어를 넣지 않았다(지시서도 "구조 확인 후 결정"이라 열어 뒀다).

### 4-3. (Phase A) 템포 트레이너 — 루프 경계에서만, 그리고 "건너뛴 루프는 세지 않는다"

BPM을 마디 중간에 바꾸면 그 마디의 박자가 늘어지거나 줄어든다. 연습 도구로서는 치명적이라 지시서도 "루프 경계에서만"을 못박았다. 구현은 `st.idx`가 0으로 되돌아가는 지점에서만 `onLoopEnd()`를 부르고, 템포가 바뀌면 그 자리에서 `break`해 **다음 회차부터 새 템포로** 계산하게 했다.

여기에 **지시서에 없던 판단을 하나 더 했다.** 폰을 잠갔다 돌아오면 `skipPast`가 지나간 이벤트를 조용히 건너뛰는데(이슈 #15 방어), 이때 루프 경계도 여러 번 지나간다. 이걸 진도로 세면 **잠금 해제하는 순간 템포가 확 뛴다.** 그래서 `skipPast` 안에서는 `st.loops`를 올리지 않는다. 실제로 연습한 바퀴만 세는 것이 맞다.

**수동 우선:** 사용자가 BPM 슬라이더를 만지면 트레이너가 해제된다(`setBpmManual`). 트레이너가 올린 값과 사용자가 정한 값이 싸우면 안 되기 때문이다.

### 4-4. (Phase C) 팁을 "데이터 + 순수 함수"로 둔 이유

`src/theory/tips.js`는 React에 의존하지 않는다(`theory/` 규칙). 팁은 `{ id, where, cond, text, more }`이고 `cond`는 현재 선택 상태를 받는 순수 함수다. 덕분에 **팁이 주장하는 내용을 테스트에서 앱 데이터로 다시 계산해 검증**할 수 있다 — 이 앱의 "이론은 전부 사실 검증 후 수록" 원칙을 팁에도 그대로 적용한 것이다.

지시서가 금지한 과설계(우선순위 점수, 노출 빈도 알고리즘)는 넣지 않았다. `pickTip`은 조건 맞는 **첫 팁 하나**를 돌려준다.

**닫힘 상태를 저장하지 않은 것도 지시서 그대로다.** 모듈 수준 `Set`으로 세션 동안만 기억한다. 조건이 바뀌면(다른 코드·다른 스케일) 다시 보이는 편이 쓸모 있기 때문이다.

**용어 사전(C-3):** 별도 화면을 만들지 않고, 팁을 펼쳤을 때 그 안에 나온 용어만 최대 2개까지 한 줄로 풀어 준다. 12개 항목을 뒀다.

### 4-5. (Phase B) 코드톤 강조의 시각 언어 — 금색과 싸우지 않게

지시서 §4가 "루트음 금색은 유지하되 코드톤 강조가 금색과 경쟁하지 않게"를 조건으로 걸었다. Phase 3에서 정한 원칙(금색 = 선택된 것·루트음)을 깨면 안 되기 때문이다.

→ **코드톤 강조는 teal 계열로 완전히 분리했다.** 가이드톤(3·7음)은 **이중 테두리 + 밝은 채움**, 그 밖 코드톤은 **테두리 굵게**, 코드 밖 음은 **투명도 0.3**으로 흐리게. 지우지 않고 흐리게만 한 이유는 여기가 스케일 학습 화면이라 전체 모양이 보여야 하기 때문이다. 루트음은 예전처럼 금색을 유지하고, 그것이 코드톤이기도 하면 금색 이중 테두리가 된다.

갱신은 `nowChord`를 그대로 재사용한다(절대 규칙 7). 코드가 바뀔 때만 다시 계산되고, 잼이 멈춰 있으면 `chordTones`가 `null`이라 **예전 화면과 완전히 같다**.

### 4-6. (Phase C-4) 팝/락 진행 미니플레이어 — 이번에도 보류

3부 §3-14에서 대기하던 항목이다. 지시서는 (a) 트라이어드 스트럼 컴핑을 새로 만들기 / (b) 보류 중 택일을 요구했고, 발주자가 **(b) 보류**를 선택했다. 판단 근거는 3부에 적은 그대로다 — 지금 컴핑 엔진은 4음 드롭2 전용이라 트라이어드 진행에 쓰면 원래 없던 7음이 붙고, 별도 엔진을 만들면 작업량이 중간 이상이다.

### 4-7. (Phase D) 연습 탭 — 시안 제시 후 보류

와이어프레임 3화면(진입 화면·지판 퀴즈 진행 중·귀 훈련 정답 후)을 저장소 밖에서 정적 HTML로 만들어 아이폰 크기로 렌더해 제시했다. 발주자 판단은 **보류**. 제시할 때 함께 전한 우려는 두 가지였다 — ① A·B·C를 합친 것보다 작업량이 크다, ② 제안서 스스로 밝힌 "한 화면 = 한 질문" 미덕과 연습 탭 안의 4개 모드가 충돌한다.

## 5. 검증 방법론 (이번 세션 추가분)

1~3부의 (A)~(Q)에 더해:

- **(R) 의도한 변경의 국한 증명.** 이번엔 소리를 일부러 바꾸는 항목(카운트인)이 있어 "아무것도 안 바뀌었다"를 증명할 수 없다. 대신 **세 가지를 나눠 증명**했다 — ① `jamTimeline`이 1,728가지 조합에서 결정적이고 카운트인을 인자로 받지도 않음, ② 카운트인은 `st.loopStart`만 밀고 `timeline` 배열은 `push/splice/unshift`조차 하지 않음(정적 검사), ③ 컴핑 끄기는 `strumAt` 호출만 조건 안에 넣고 드럼·코드 표시는 밖에 둠(중괄호 짝을 맞춰 블록 본문을 잘라 확인). 절대 규칙 11이 요구한 "변경이 의도한 항목에만 국한됨"의 구체적 형태다.
- **(S) 콘텐츠 사실 검산.** 팁이 주장하는 이론을 **테스트에서 앱 데이터로 다시 계산**한다. 가이드톤 하강(12키), 이웃 키 공통음(12쌍), 펜타↔블루스 차집합, CAGED 겹침(12루트), 마이너 251 V7의 하모닉 마이너·♭9·♭13(12키), 턴어라운드 마디 수. 문구가 바뀌어도 사실과 어긋나면 실패한다.
- **(T) 예약 창을 고려한 시간 시뮬레이션.** 트레이너 검사에서 오디오 시계를 **미리 예약 창(0.15초)보다 작게** 밀어야 실제 재생과 같은 흐름이 된다. 크게 밀면 이벤트가 전부 과거가 되어 `skipPast`로 건너뛰어지고(= 폰을 잠근 상황), 루프 경계도 지나가 버려 "트레이너가 안 도는 것처럼" 보인다. 이 함정을 검사 파일 주석에 남겨 뒀다.

## 6. 알려진 한계 / 리스크 (갱신)

- **템포 트레이너의 상한은 200BPM이다.** BPM 슬라이더 최대가 200이라 목표도 그 안에서만 잡힌다. 더 빠른 연습이 필요하면 슬라이더 상한부터 논의해야 한다.
- **카운트인 길이는 4박 고정.** 2박·8박 선택은 넣지 않았다(지시서에 없고, 선택지가 늘면 시트가 복잡해진다).
- **컴핑을 꺼도 드럼은 끌 수 없다.** 현재 구조에서 드럼은 상시 재생이다. "완전 무음 + 코드 표시만" 모드가 필요하면 별도 작업이 필요하다.
- **팁은 화면당 1개, 조건 맞는 첫 하나다.** 두 조건이 동시에 맞으면 배열 순서가 이긴다. 순서가 곧 우선순위이므로 팁을 추가할 때 위치를 신경 쓸 것.
- **코드톤 타겟 뷰는 스케일 안의 음만 다룬다.** 코드톤이 스케일 밖이면 애초에 지판에 그려지지 않는다(예: C 메이저 위 E7의 G♯). 스케일 학습 화면이라는 성격상 의도된 동작이지만, "코드 밖 음도 보고 싶다"는 요구가 생기면 재논의 대상이다.
- **옛 주소 정리는 발주자 손이 필요하다.** `docs/index.html`의 Vercel 주소를 실제 주소로 바꾸고, GitHub 저장소 Settings → Pages에서 소스를 `main` 브랜치 `/docs` 폴더로 바꿔야 노출된다.
- **VoiceOver 실사용 검증은 여전히 없다.** 새로 만든 토글에는 `role="switch"`와 `aria-checked`를 넣었지만 실제 낭독기 테스트는 못 했다.

## 8. 검토 시 유의점 (1~3부에 추가)

1. **팁을 추가·수정하면 사실 검산부터.** `tests/tips.test.jsx`의 "팁 내용 사실 검증" 블록처럼, 주장하는 내용을 앱 데이터로 다시 계산하는 검사를 함께 넣을 것. 이론에 밝은 사람이 쓴 문장도 틀릴 수 있다(이슈 #17·#18·#20이 전부 그랬다).
2. **`skipPast` 안에서 `st.loops`를 올리지 말 것.** 폰을 잠갔다 돌아왔을 때 템포 트레이너가 확 뛴다.
3. **컴핑 조건 블록 안에 `setNowChord`를 넣지 말 것.** 메트로놈 모드의 핵심(코드를 눈으로 따라가기)이 사라진다. 정적 검사가 막고 있다.
4. **카운트인을 `jamTimeline` 안으로 옮기지 말 것.** 지금 구조라야 "반주 데이터는 그대로"를 구조로 증명할 수 있다.
5. **코드톤 강조에 금색을 쓰지 말 것.** 금색은 선택 상태와 루트음 전용이다(3부 §3-16). 코드톤은 teal 계열로 분리돼 있다.
6. **잼 시트가 길어지고 있다.** 키·폼 / 코드 줄 / 보이싱 지판 / 리듬·음색·드럼 / 연습 / 팁 / 재생·BPM 순이다. 여기에 더 얹기 전에 구역을 접거나 나누는 편이 낫다.
